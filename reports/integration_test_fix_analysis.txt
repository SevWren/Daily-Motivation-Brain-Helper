PROBLEM 1: New-ScheduledTaskAction Mock
----------------------------------------
DailyMotivation.ps1 Line 728 calls:
```powershell
$action = New-ScheduledTaskAction -Execute $exeForTask -Argument "/popup"
```

The mock uses `$args[0]` to capture the Execute parameter, but:
- Named parameters don't populate $args in PowerShell
- $args[0] will be $null
- The mock returns Execute = $null

This doesn't directly cause Success=$false (no validation on action object),
but it creates an invalid action object.

PROBLEM 2: New-ScheduledTaskTrigger Mock
-----------------------------------------
DailyMotivation.ps1 Lines 734-739:

The mock:

- Line 739 tries to SET $trigger.EndBoundary

When a PSCustomObject property is created with value '', attempting to set

LESSON LEARNED
--------------
When debugging test failures:
1. Compare mock patterns across different test files
2. Question whether mocks are necessary (especially for native cmdlets)
3. Verify mock parameter handling matches actual cmdlet usage
4. Prefer native cmdlets over mocks when platform-specific tests allow it
5. Start with "are the mocks correct?" before "is the function logic wrong?"

GENERAL PRINCIPLE
-----------------
Mock at the boundary, not the internals:
- Integration tests should mock the OS interaction boundary (Register/Get/Unregister)
- Don't mock internal object creation (New-ScheduledTask* cmdlets)
- Let native code run when it works correctly

This follows the same principle as not mocking System.IO.Path or Get-Date -
these are reliable primitives that should just work.
